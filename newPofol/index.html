About

현상보다 구조를 먼저 보는 개발자

사용자가 체감하는 문제를 단순 장애나 느린 응답으로 보지 않고, 반복되는 원인이 구조 안에 있는지 먼저 확인합니다. 그래서 설계, 동시성 제어, 캐시, 관측 지표까지 한 흐름으로 연결해 해결합니다.

01

문제 정의

병목이 생긴 지점보다 병목이 만들어진 이유를 먼저 좁힙니다. 락, 대기열, 캐시 모두 현상 대응이 아니라 원인 분리를 위한 선택으로 접근했습니다.

02

적정 복잡도

복잡한 기술을 먼저 채택하지 않습니다. Redis 락과 DB 조건부 차감을 같은 시나리오로 비교해 현재 환경에서 더 단순하고 빠른 구조를 선택했습니다.

03

검증 습관

JMeter, Grafana, Prometheus 기반으로 결과를 수치화하고, 실제로 운영 가능한지까지 확인하는 방식을 선호합니다.

Principles

포트폴리오를 관통하는 세 가지 기준

Define

문제 상황을 재현 가능한 시나리오로 바꿉니다

쇼핑몰 주문 경쟁 시나리오, 티켓팅 200명 혼잡 시나리오처럼 실제 충돌이 발생하는 구간을 먼저 명확히 만들고 설계를 시작했습니다.

Design

사용자 요청과 시스템 내부 처리를 분리합니다

대기열로 입장 흐름을 나누고, Kafka 비동기로 결제 처리를 분리해 병목이 한 지점으로 몰리지 않도록 구성했습니다.

Verify

선택한 구조가 맞는지 끝까지 검증합니다

처리량, 지연 시간, 최종 재고, 활성 슬롯 유지 여부까지 함께 보고 성능과 정합성을 동시에 확인했습니다.

Project 01

쇼핑몰 API 서버

1인 개발 · 2026.01 - 2026.02 · Spring Boot / Redis / PostgreSQL

GitHub 저장소

주문 정합성과 조회 성능을 함께 검증한 쇼핑몰 서버 프로젝트입니다. 동시 주문에서 재고 무결성을 보장하고, 현재 환경에 맞는 동시성 제어 방식을 PoC로 비교해 적정 복잡도를 선택했습니다.

  • 동시성 제어
  • 재고 정합성
  • PoC 검증
  • Redis 캐시

Integrity

동시 주문 환경에서 재고 정합성 보장

  • 상품별 Redis 락과 DB 조건부 차감을 함께 적용해 oversell을 방지했습니다.
  • 락 획득 실패는 429, 재고 부족은 409로 나눠 실패 원인을 명확히 구분했습니다.
  • 재고 100개에 140건 요청이 들어오는 통합 테스트에서도 성공 100건, 실패 40건, 최종 재고 0개를 유지했습니다.

PoC

Redis 락과 DB 조건부 차감을 비교해 더 단순한 구조를 선택

  • 동일 주문 API에 두 가지 전략을 적용해 처리량, 응답 지연, 정합성을 함께 비교했습니다.
  • 단일 인스턴스 환경에서는 DB 조건부 차감만으로도 무결성을 유지할 수 있음을 확인했습니다.
  • 최대 처리량은 약 1.5k req/s에서 4.3k req/s로, p95 지연은 200~450ms에서 150~220ms로 개선됐습니다.

Cache

반복 조회 패턴을 기준으로 캐시 효과를 검증

  • 약 100만 건 데이터를 적재한 뒤, 인기 페이지 10개와 랜덤 페이지 50개 시나리오로 비교했습니다.
  • Redis 캐시 적용 후 warm-up 제외 기준으로 p50 약 3ms, p95 약 18~21ms 수준을 유지했습니다.
  • 캐시는 단순 속도 개선이 아니라 키 설계, TTL, 무효화, 장애 시 DB fallback까지 포함한 일관성 설계로 접근했습니다.

Project 02

티켓팅 서버

1인 개발 · 2026.02 · Spring Boot / Kafka / Redis / PostgreSQL

GitHub 저장소

대기열, 활성 슬롯, 비동기 결제를 결합해 혼잡 구간의 예매 흐름을 안정적으로 통제한 프로젝트입니다. 사용자가 자신의 상태를 이해할 수 있고, 운영자는 병목을 관찰할 수 있는 구조에 집중했습니다.

  • Redis ZSET 대기열
  • Lua 원자 처리
  • Kafka 비동기 결제
  • 관측 대시보드

Queue

대기열과 활성 슬롯으로 동시 진입량을 제한

  • Redis ZSET 기반 대기열로 사용자 순번을 관리하고, 활성 슬롯은 최대 20명으로 제한했습니다.
  • 입장 토큰은 Lua 스크립트로 원자적으로 발급해 경쟁 상태에서도 순서가 흐트러지지 않도록 했습니다.
  • RampUp 20으로 누적 요청 200명을 발생시킨 혼잡 시나리오에서 대기열은 약 172명까지 증가했지만, 활성 슬롯은 20명으로 유지됐습니다.

Flow

결제와 재고 처리를 비동기로 분리해 혼잡 구간을 흡수

  • 결제 요청은 Kafka 이벤트로 분리해 사용자 요청 흐름과 내부 처리 흐름이 같은 구간에서 충돌하지 않도록 설계했습니다.
  • 멱등성 키와 TTL 가드를 적용해 중복 결제 요청을 방지했습니다.
  • JWT 기반 인증과 관리자 API를 함께 구성해 운영 중 제어와 점검이 가능한 상태를 만들었습니다.

RampUp 20

누적 요청 200명 발생 혼잡 시나리오

혼잡 구간에서 대기열은 일시적으로 약 172명까지 증가했지만, 활성 슬롯은 누적 요청 인원의 10% 수준인 20명으로 유지됐습니다. 실제 운영 환경은 아니지만 입장 흐름과 결제 처리를 분리했을 때 처리 한계를 넘지 않고 안정적으로 동작한다는 점을 확인했습니다.

  • 활성 슬롯이 20명 수준으로 유지되는지 확인
  • 대기 사용자가 줄어드는 동안 처리 이벤트가 급증하지 않는지 확인
  • 슬롯 반환과 만료가 정상적으로 순환하는지 확인
