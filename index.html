대기열 / 활성 슬롯 분리

DB 조건부 차감 단독 검증

정합성
AS-IS

동일 상품에 주문이 동시에 몰리면 재고가 중복 차감되거나 음수가 될 가능성이 있었습니다. Redis 락 없이도 최종적으로 초과 주문을 막을 수 있는 안전장치가 필요했습니다.

TO-BE

분산 락을 먼저 도입하기보다, DB 차감 쿼리만으로 어디까지 정합성이 보장되는지 먼저 확인했습니다. 재고가 0보다 클 때만 차감되는 조건부 쿼리를 적용하고, 영향받은 행 수가 0이면 재고 부족으로 처리했습니다.

Redis 락으로 처리 직렬화 + 응답 분류

Redis
AS-IS

DB 조건부 차감만으로 초과 주문은 막을 수 있었지만, 동일 상품에 대량 요청이 몰릴 때 처리 결과가 성공/재고부족만으로 분리되어 재시도 가능한 일시적 경합과 재고 소진을 구분할 수 없었습니다.

TO-BE

상품 ID 기준 lock:product:{productId} Redis 락으로 처리 흐름을 직렬화하고, Lua 스크립트로 토큰을 검증한 뒤 락을 해제해 다른 요청의 락을 잘못 풀지 않도록 했습니다. 응답은 201(성공) / 409(재고 부족) / 429(락 경합) / 5xx로 분리해 클라이언트가 다음 행동을 결정할 수 있게 만들었습니다.

주의 · 로컬 Docker 단일 상품 집중 테스트 결과로 "Redis가 항상 빠르다"가 아닌, 같은 조건에서 두 경로의 처리 흐름·실패 분류·지연 시간이 어떻게 달라지는지 관측한 자료입니다. 운영 분산 환경의 락 경합 안정성까지 검증한 것은 아닙니다.

캐시 적용 전후 latency 비교

tail latency
AS-IS

반복 조회가 많은 상품 목록은 사용자가 가장 자주 체감하는 구간이지만, DB 직접 조회만으로는 페이징 쿼리의 tail latency가 일정하지 않게 튀는 문제가 있었습니다.

TO-BE

캐시 적용 시나리오와 비캐싱 시나리오를 나눠 목록 조회 latency를 비교했습니다. warm-up 구간은 비교에서 제외했습니다.

구간p50p95p99
캐시 적용~3 ms18–21 ms22–26 ms
비캐싱~18–19 ms22–27 ms25–28 ms

캐시 적용 시 tail latency가 더 낮고 변동도 작았습니다. 평균 응답보다 p95 / p99가 사용자 체감에 더 큰 영향을 준다는 가정을 지표로 확인했습니다.
